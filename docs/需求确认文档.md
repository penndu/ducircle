## 一、项目定位

**一句话**：把「hexo-circle-of-friends」从个人自用工具，重写为面向陌生博主的公开 SaaS 服务。

| 维度 | 结论 |
|---|---|
| 使用者 | 公开服务，任何博主注册即用 |
| 核心用途 | 展示友链最新文章 + 活跃度统计 + 好友圈管理 + AI 摘要推荐 |
| 运行形态 | Docker 镜像，`docker compose up` 一条命令 |
| 运行位置 | 自有 VPS + Nginx/Caddy 反代 |
| 用户规模 | 几百人量级（2核2G 足够） |
| 交付周期 | 半年，做扎实 |
| 维护方式 | 开源，接受外部 PR |

## 四、抓取策略（核心设计）

### 4.1 四层策略与优先级

**用户自定义规则优先级最高** —— 用户配了就完全信任，不再自动推断。

```
第0 层  用户自定义规则（数据库，priority = 100）
         ↓ 未命中
第 1 层  RSS/Atom 自动发现
         ↓ 失败
第 2 层  框架指纹识别（meta generator）
         ↓ 未识别
第 3 层  通用结构推断（启发式）
         ↓ 失败
         标记失败，进后台「抓取失败列表」等待人工介入
```

### 4.2 各层实现

**第 1 层 RSS 自动发现**（实测抽样 3/3 命中）
1. 解析 HTML `<link rel="alternate" type="application/rss+xml">`
2. 依次探测常见路径：`/atom.xml`、`/feed.xml`、`/rss.xml`、`/index.xml`、`/feed`
3. 全部失败则回退到站点根目录

**第 2 层 框架指纹**（实测抽样 3/3 命中）
读取 `<meta name="generator">`，识别 Hexo / Hugo / WordPress / VuePress / VitePress / Astro / Gatsby / Nuxt。
每个框架对应内置的通用解析规则（文章列表容器、文章链接模式、日期字段）。

**第 3 层 通用结构推断**
启发式规则：识别 `<article>` / `<h2><a>` 模式、`<time>` 标签、常见博客 class 命名（`post-*`、`entry-*`、`article-*`）。

**第 0 层 用户自定义规则**
数据库存储，结构与现有 `css_rules.yaml` 兼容但改为数据库表。后台可视化编辑。

### 4.3 关键约束

- 尊重 `robots.txt`
- 带可识别的 User-Agent
- 全局+ 单站点限速
- 命中缓存，避免重复抓取
- 只抓用户自己配置的友链及其文章，不主动爬站外

## 五、数据模型

### 5.1 多租户隔离

**共享库 + 全表 `user_id` + ORM 层强制注入过滤**

不是「靠业务代码记得加 `WHERE user_id = ?`」，而是在 SQLAlchemy 事件钩子里自动注入，业务代码**写不出**无过滤查询。这是开源项目能接受的安全底线。

### 5.2 核心表

| 表 | 说明 | 关键字段 |
|---|---|---|
| `users` | 用户 | id, username, password_hash, ai_provider, ai_api_key, api_token, quota_limit |
| `sites` | 友链站点 | id, user_id, name, url, feed_url, avatar, source, active, error, last_success_at |
| `site_rules` | 自定义抓取规则 | id, user_id, site_id, field, selector, attr, priority, enabled |
| `posts` | 文章 | id, user_id, site_id, title, link, guid_hash, created, updated, summary, ai_score, ai_model |
| `crawl_logs` | 抓取记录 | id, user_id, site_id, status, strategy_used, error, duration_ms, created_at |
| `tags` / `site_tags` | 标签分组 | id, user_id, name / site_id, tag_id |
| `ai_quota_logs` | AI 额度消耗 | id, user_id, date, count |
| `blacklist` | 黑名单 | id, user_id, pattern, is_regex |

**唯一约束**：`posts` 上 `(user_id, guid_hash)` 唯一 —— `guid_hash` 为规范化 link 的 SHA1，用于去重。

## 六、技术栈

| 层| 选型 | 理由 |
|---|---|---|
| 语言 | Python 3.12 | 单一语言消灭双实现问题 |
| Web 框架 | FastAPI | 自带 OpenAPI，异步原生 |
| ORM | SQLAlchemy 2.0 | `with_loader_criteria` 做强制过滤 |
| 数据库 | MySQL 8 | 复用服务器已有实例 |
| 调度 | APScheduler | 轻量，无需额外中间件 |
| 缓存/限流 | Redis | 缓存 + 令牌桶限流 |
| HTML 解析 | selectolax | 速度快 |
| 正文抽取 | trafilatura | 专为 AI 摘要设计 |
| Feed 解析 | feedparser | 标准库 |
| 前端 | Tailwind + Jinja2 | 无需构建链，中文界面，响应式 |
| 认证 | Session + API Key 双轨 | 后台用 Session，API 用 Key |
| 部署 | Docker Compose | 一条命令 |

## 七、非功能需求

### 7.1 性能

- 每用户抓取并发默认 10，全局默认 50，后台可配
- 单站超时默认 30 秒，失败重试 3 次，指数退避
- API 响应缓存 TTL 60 秒
- 目标：100 站点完整抓取 ≤ 3 分钟，成功率 ≥ 95%

### 7.2 安全

- 密码 bcrypt 哈希
- API Key 用于只读接口，Session 用于后台
- QPS 限流（每用户）+ 全局并发上限
- Redis 缓存防重复抓取
- User-Agent 标识 + 遵守 robots.txt

### 7.3 合规

- 摘要仅供用户自己判断，不二次分发全文
- 不抓取付费 / 登录后可见内容
- 支持一键删除某站点全部数据（站点博主下架请求）
- 提供站点所有者申诉下架入口

### 7.4 可观测

- 结构化日志（JSON）
- 每次抓取写 `crawl_logs`
- 后台可见抓取成功率、最近失败列表
