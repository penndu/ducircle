## 三、关键设计决策

### 3.1 ORM 层强制租户过滤（解决开源安全风险）

**问题**：共享库 + `user_id` 靠业务代码记得加过滤，在开源项目里必然被 PR 漏掉。

**方案**：在 SQLAlchemy 的 `do_orm_execute` 事件上挂全局钩子。

```python
@event.listens_for(Session, "do_orm_execute")
def _inject_tenant_filter(state):
    """对所有租户表自动追加 user_id 条件。"""
    ctx = get_current_tenant()          # ContextVar 持有当前用户
    if ctx is None or ctx.is_system:     # 系统任务或后台管理可豁免
        return
    for mapper in state.iter_mappers():
        if mapper.local_table.name in TENANT_TABLES:
            state.statement = state.statement.where(
                mapper.class_.user_id == ctx.user_id
            )
```

**效果**：业务代码写 `session.query(Post)` 出来就自带 `WHERE user_id = ?`，物理上无法构造跨租户查询，除非显式调用 `session.no_tenant_filter()` —— 该方法在代码审查时一眼可见。

**兜底**：集成测试用两个用户的数据做交叉断言，越权即测试失败。

### 3.2 抓取四层策略

```
用户自定义规则（priority=100）
      │ 未命中
      ▼
RSS 自动发现 ──── 成功 ──→ 结束
      │ 失败
      ▼
框架指纹识别 ─── 命中 ──→ 按框架规则解析
      │ 未识别
      ▼
通用结构推断 ─── 成功 ──→ 结束
      │ 失败
      ▼
写入 crawl_logs(status='failed') → 后台失败列表
```

**关键**：每层的结果和命中策略都记入 `crawl_logs.strategy_used`，便于统计各层实际贡献率 —— 这是持续优化规则覆盖的唯一依据。

### 3.3 文章去重

```python
guid_hash = sha1(normalize_url(article_link).encode()).hexdigest()
# normalize_url: 统一协议、去掉 www.、去掉末尾斜杠、去掉 utm_* / from / ref 等追踪参数
# 唯一约束: UniqueConstraint(user_id, guid_hash)
```

**为什么不用标题+作者**：不同博客常有同名文章（《Hello World》满天飞），标题去重会误杀。URL 规范化后去重更准，同时能识别博主换域名后的老链接（老域名重定向也能命中）。

### 3.4 AI 摘要与额度

```python
# 优先级
if user.ai_api_key:                    # 用户自带 Key
    provider = user.ai_provider
elif quota_remaining(user) > 0:        # 平台额度
    provider = PLATFORM_DEFAULT
else:
    raise QuotaExceeded()

# 内容哈希缓存：文章 HTML 变了才重新生成，避免重复花钱
content_hash = sha1(article_html).hexdigest()
if existing and existing.content_hash == content_hash:
    return existing.summary
```

**额度统计**：按 `(user_id, date)` 聚合 `ai_quota_logs` 计数，超额直接拒绝并提示。

### 3.5 限流设计

```python
# 双层限流
user_bucket   = Redis 令牌桶(f"{user_id}", rate=10, capacity=30)   # 每用户
global_bucket = Redis 令牌桶("global", rate=100, capacity=200)      # 全局
```

**抓取并发**：用 Redis 信号量（`INCR`/`DECR` + 超时保护）而非进程内 Semaphore，因为限流和调度可能跑在不同进程。

### 3.6 Docker 部署

单容器应用 + compose 编排 MySQL / Redis：

```yaml
services:
  app:    # FastAPI + APScheduler
  mysql:  # 8.0
  redis:  # 7-alpine
```

- 应用容器同时跑 API 和调度器（几百人规模足够，2核2G 撑得住）
- 保留 `worker` profile 开关，需要时单独扩一个抓取进程
- 首次启动自动 `alembic upgrade head`

## 四、数据库设计要点

| 关注点 | 做法 |
|---|---|
| 多租户查询性能 | 所有查询走 `(user_id, ...)` 复合索引 |
| 文章列表分页 | `(user_id, created DESC)` 复合索引，游标分页 |
| 日志表膨胀 | `crawl_logs` 按月分区，定期归档 |
| 软删除 | `sites` / `posts` 带 `deleted_at`，支持"某站全部数据一键删除" |
| 活跃度统计 | `sites.last_success_at` + `posts` 聚合，配合物化视图或定时快照 |

## 五、风险与对策

| 风险 | 等级 | 对策 |
|---|---|---|
| 友链页结构千奇百怪，自动识别覆盖不全 | 高 | 用户自定义规则兜底 + 失败列表人工介入 + 按 `strategy_used` 统计持续优化 |
| 抓取被对方站点限流或封禁 | 中 | 限速 + UA 标识 + 指数退避重试 + 失败站点降频调度 |
| AI 摘要成本失控 | 中 | 平台额度 + 内容哈希缓存 + 用户自带 Key |
| 跨租户数据泄露 | 高 | ORM 强制过滤 + 集成测试交叉断言 + CI 检查 |
| 管理员误操作把平台锁死 | 中 | 服务端禁止停用/降权/删除自己；首个账号自动成为管理员 |
| 公开注册被批量刷号 | 中 | 注册接口独立限流桶 + `ALLOW_REGISTRATION` 可整体关闭 + 管理页按 IP/时间定位异常账号 |
| 定时任务重复执行 | 中 | Redis 分布式锁保证同一任务全局单例 |
| 磁盘被日志撑满 | 低 | 日志按月分区 + logrotate + 结构化日志 |

## 七、多用户平台与权限（v2.0.0）

### 7.1 三种身份

| 身份 | 认证方式 | 能做什么 |
|---|---|---|
| 访客 | 无 | 看落地页、注册、看 API 文档 |
| 用户 | Session Cookie（后台）/ API Key（`/v1/*`） | 管理自己的友链、文章、摘要、导出数据 |
| 管理员 | Session Cookie + `is_admin` | 上面全部，外加 `/web/admin/users` 与 `/api/admin/users*` |

管理员权限只由 `users.is_admin` 决定，与用户名、ID 无关。
`is_admin` 没有自助入口——只能由现有管理员在管理页授予。

### 7.2 管理员跨租户查询为什么要显式豁免

认证依赖（`get_current_user_session` / `get_current_user_key`）在解析出用户后
会 `set_tenant(user.id)`。管理员登录后，租户上下文里是他**自己**的 ID。

于是管理页最危险的一类 bug 是：

```python
# ❌ 看起来在统计全站，实际只会返回管理员自己的数字
total = (await db.execute(select(func.count(Site.id)))).scalar_one()
```

两个数字长得一模一样，页面上完全看不出错。正确写法必须显式豁免：

```python
async with no_tenant_filter_async():
    total = (
        await db.execute(
            select(func.count(Site.id)).where(Site.user_id == target_id)
        )
    ).scalar_one()
```

`no_tenant_filter_async` 在代码审查时一眼可见，不会被无声漏掉。
测试 `tests/test_admin_users.py::TestOverviewIsCrossTenant` 专门守这条。

### 7.3 管理员不能把自己锁在门外

三条硬性拒绝（服务端，不只靠前端隐藏按钮）：

- 不能停用自己的账号
- 不能撤销自己的管理员权限
- 不能删除自己的账号

理由：平台可能出现「只有一个管理员」的状态，一次误点就再也没人能进管理页，
只能连数据库手改。这三条在 `app/api/admin_users.py` 的 `update_user` /
`delete_user` 里显式判断。

### 7.4 API 跨站

`/v1/*` 只读、用 `X-API-Key` 鉴权、**不依赖 Cookie**，因此放开跨域来源
不会引入 CSRF 风险。`CORS_ORIGINS` 默认 `*`（不限制调用网站），
也可以填域名白名单收紧。

`/api/*` 与 `/web/*` 靠 Cookie 会话鉴权，**永远不返回 CORS 头**——
`CorsMiddleware` 只处理以 `/v1/` 开头的路径，这是硬编码的边界。
